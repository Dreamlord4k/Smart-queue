# PLAN.md

> Полная схема данных (все поля/типы), полный список API-эндпоинтов, рекомендации по стеку и деталям инфраструктуры — см. `docs/TECH_SPEC.md`. Этот файл (PLAN.md) — стратегия по этапам, не дублирует точные схемы.

## Этап 1. Аккаунты, роли, группы

Реализация: регистрация/логин (bcrypt/argon2 хэш пароля), JWT access (короткий TTL) + refresh (долгий TTL), роль в токене (`student`/`teacher`), сущность `Group`, у студента `group_id`.
Затрагивает: `backend/auth/*`, `backend/models/user.py`, `backend/models/group.py`.
Проверка: unit-тесты на регистрацию/логин/refresh, интеграционный тест «неверная роль не может дёрнуть чужой эндпоинт».
Критерий: после логина сессия переживает перезапуск клиента без повторного ввода пароля.
Зависит от: нет.

## Этап 2. Сессии приёма, автоматическая очередь и дашборды

Реализация: `Session` (course_name, room, date, start_time, duration_default, capacity, status, frozen), эндпоинт создания сессии с мультивыбором групп/студентов. В одной транзакции создать `QueueEntry` для каждого уникального выбранного студента, отсортировав по ФИО; RSVP и приглашение-подтверждение не реализуются. `GET /sessions/mine` — список сессий преподавателя; `GET /students/me/queues` — главный экран студента со всеми активными и предстоящими очередями и их независимыми статусами.
Затрагивает: `backend/models/session.py`, `backend/models/queue_entry.py`, `backend/routes/sessions.py`, `backend/routes/queue.py`, `frontend/src/screens/TeacherDashboard.tsx`, `frontend/src/screens/MyQueues.tsx`.
Проверка: тест «создание сессии сразу создаёт алфавитную очередь всех приглашённых», тест «пустая активная очередь не переводит сессию в cancelled», тест «дашборд студента показывает несколько сессий одного дня с независимыми статусами и предупреждением о потенциальном пересечении».
Критерий: состояние сессии меняет только преподаватель; отсутствие активных участников не отменяет её. Карточка каждой очереди показывает предмет, преподавателя, аудиторию, дату и время, позицию, ETA и статус участия.
Зависит от: Этап 1.

## Этап 3. Очередь, EMA/ETA, каналы (capacity)

Реализация: `QueueEntry` (position, status, channel, absence_reason), формулы EMA (`alpha=0.3`) и ETA с учётом нескольких параллельных каналов (жадное распределение по `channel_free_at`), действие студента «Не смогу участвовать» с необязательной причиной и кнопка «Завершить текущую» (завершает канал + сразу поднимает следующего). Отказ помечает только данную запись как `absent`, не удаляет её и исключает из расчёта активной очереди.
Затрагивает: `backend/queue/eta.py`, `backend/routes/queue.py`.
Проверка: unit-тесты на формулу EMA (разные входные real_time), unit-тесты на распределение по каналам при `capacity=1` и `capacity>1`, интеграционный тест «отказ сохраняет absence_reason, исключает только запись данной сессии и пересчитывает позиции и ETA остальных».
Критерий: при `capacity=2` система корректно ведёт два параллельных ETA-потока одновременно.
Риск: неверный расчёт при одновременном освобождении нескольких каналов (гонка).
Откат: для MVP допустимо последовательно обрабатывать завершения одной транзакцией (без настоящего параллелизма каналов).
Зависит от: Этап 2.

## Этап 4. Self-service реордер, фиксация и заморозка списка

Реализация: эндпоинт «встать перед/после карточки X» только для собственной активной записи; проверка на бэкенде, что целевое место не занято `locked=true` записью; чек-марк `locked` + `lock_reason` (свободный текст); отдельный `absence_reason`; `QueueMoveLog`; teacher-only действие «Заморозить список», устанавливающее `session.frozen=true`.
Затрагивает: `backend/routes/queue.py` (reorder-эндпоинт), `backend/models/queue_entry.py`.
Проверка: тест «студент не может подвинуть чужую запись» (403), тест «нельзя встать на locked-место», тест «нельзя двигать себя после того как сам locked=true», тест «после заморозки никто не меняет порядок», тест «lock_reason и absence_reason хранятся и отображаются раздельно».
Критерий: попытка нарушить любое из правил возвращает явную ошибку, а не тихий no-op; `locked` блокирует одну запись, а `frozen` — изменение порядка всей очереди.
Зависит от: Этап 3.

## Этап 5. Уведомления (Telegram)

Реализация: линковка `telegram_id` к существующему аккаунту (одноразовый код через бота), три типа уведомлений (мягкое по таймеру, буферное и финальное по событию `done`/`skip`), фоновая задача пересчёта мягких уведомлений.
Затрагивает: `bot/*`, `backend/notifications/*`.
Проверка: интеграционный тест «после done у второго в очереди появляется buffer-уведомление, у первого — hard_call», лог в `NotificationLog` не дублирует отправку.
Критерий: ни одно уведомление не отправляется дважды одному и тому же событию.
Зависит от: Этап 3.

## Этап 6. Реалтайм-слой

Реализация: Redis pub/sub на канал `session:{id}`, WebSocket-рассылка изменений очереди подписанным клиентам; fallback — long-polling каждые 5 секунд, если WS не успеваем.
Затрагивает: `backend/realtime/*`, `frontend/src/hooks/useQueueSocket.ts`.
Проверка: ручная проверка — два открытых окна (студент/препод) видят изменения без ручного рефреша.
Риск: не успеть с WebSocket за отведённое время.
Откат: long-polling — явно пометить в коде как временное решение.
Зависит от: Этап 3.

## Этап 7. Синтетический генератор данных и демо-сценарий

Реализация: скрипт создаёт группы/студентов и минимум две сессии одного дня для одного студента, автоматически заполняет очереди, эмулирует отказ с причиной, перестановку и фиксацию места, заморозку списка и ход приёма со случайной задержкой вокруг заданной длительности.
Затрагивает: `scripts/generate_demo_data.py`.
Проверка: ручной прогон перед защитой воспроизводит сценарий из §16 (демо-сценарий) без ошибок.
Зависит от: Этапы 1–3.

## Этап 8. Инфраструктура и деплой

Реализация: Docker + docker-compose (backend, frontend, postgres, redis, bot, nginx), HTTPS (Let's Encrypt, обязателен для Telegram webhook), минимальный CI (GitHub Actions/аналог), `/health`-эндпоинт.
Затрагивает: `docker-compose.yml`, `Dockerfile.*`, `.github/workflows/*`, `nginx/*`.
Проверка: `docker-compose up` поднимает всё локально одной командой.
Зависит от: параллельно с остальными этапами, не блокирует их.

## Общая стратегия тестирования

- Каждый этап — юнит- и интеграционные тесты на бизнес-логику (EMA/ETA, права на реордер, отказ без удаления истории, независимость очередей, отсутствие автоотмены) обязательны; RSVP-тесты и тесты «нулевых подтверждений» не допускаются.
- Интеграционные тесты — только на критический путь (регистрация → сессия → приём → уведомление), не на все ветки.
- Ручная проверка (демо-прогон) — обязательна перед защитой, отдельно от автотестов.
