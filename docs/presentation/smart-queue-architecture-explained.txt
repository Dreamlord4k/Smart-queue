SMART QUEUE — АРХИТЕКТУРА ПРОСТЫМИ СЛОВАМИ

Короткая схема
==============

Одной фразой
============

Браузер показывает React-интерфейс; NGINX принимает весь внешний трафик и
направляет его нужному сервису; FastAPI проверяет права и выполняет бизнес-
логику; PostgreSQL надёжно хранит состояние; Redis мгновенно сообщает об
изменениях; отдельный worker превращает нужные события в Telegram-уведомления.


1. Браузер и React/Vite
======================

Что это
-------
React — интерфейс студента и преподавателя. Vite собирает и запускает frontend.
Именно здесь пользователь видит сессии, очередь, примерное время ожидания,
статусы, формы и кнопки управления.

Что он делает
-------------
- отправляет обычные HTTP-запросы к API;
- открывает WebSocket для живых обновлений;
- хранит access/refresh-токены текущего входа;
- перерисовывает экран после ответа API или realtime-события;
- при обрыве WebSocket периодически перечитывает актуальное состояние.

Чего он не должен делать
-----------------------
Frontend не является источником истины и не решает, кому что разрешено.
Например, интерфейс скрывает запрещённое действие, но backend всё равно заново
проверяет владельца, роль, frozen и locked. Пользователь может подделать HTTP-
запрос, поэтому защита только кнопками в браузере была бы фиктивной.


2. Связь «браузер → NGINX»
==========================

HTTP используется для обычных операций: войти, получить список сессий,
переместить свою запись, завершить студента, получить отчёт.

WebSocket — длительное двустороннее соединение для событий. Когда преподаватель
нажимает «Завершить текущую», открытая страница студента узнаёт об изменении без
ручного обновления.

В production соединение защищается HTTPS/WSS. TLS-сертификат завершает NGINX:
снаружи данные зашифрованы, а внутри Docker-сети сервисы общаются по своим
внутренним адресам.


3. NGINX — единая точка входа
=============================

Зачем нужен
-----------
Пользователь обращается к одному домену, а за ним работает несколько сервисов.
NGINX прячет эту внутреннюю структуру и маршрутизирует запросы:

- «/» — frontend;
- «/api/... » — FastAPI;
- «/ws/... » — WebSocket FastAPI с обязательными Upgrade-заголовками;
- «/health» — проверка готовности backend;
- ACME challenge — подтверждение домена при выпуске сертификата Let's Encrypt.

Дополнительно NGINX принимает HTTPS-соединение и использует сертификат. Поэтому
не приходится настраивать TLS отдельно в React, FastAPI и worker.

Почему это удобно
-----------------
Один публичный домен, единые порты 80/443, меньше CORS-проблем, простая замена
внутреннего сервиса и отсутствие необходимости публиковать наружу PostgreSQL или
Redis.


4. Связь «NGINX → frontend»
===========================

NGINX передаёт запрос страницы frontend-контейнеру. Браузер получает HTML,
JavaScript и CSS, после чего React запускается уже на устройстве пользователя.

Важно: NGINX не исполняет React и не знает бизнес-логику. Он лишь отдаёт файлы
интерфейса и направляет сетевой трафик.


5. Связь «NGINX → FastAPI»
==========================

Запросы «/api/... » проксируются в backend. Например:

1) преподаватель нажал «Завершить текущую»;
2) React отправил POST-запрос;
3) NGINX направил его FastAPI;
4) FastAPI проверил JWT, роль и владение сессией;
5) backend в одной операции обновил очередь и статистику в PostgreSQL;
6) backend опубликовал realtime-событие в Redis;
7) клиент получил сигнал и перечитал свежее состояние.

Для «/ws/... » NGINX сохраняет режим WebSocket. Сам WebSocket также проверяется:
студент может подписаться только на сессию, где есть его QueueEntry, а
преподаватель — только на собственную сессию.


6. FastAPI backend
==================

Это центральный управляющий слой системы. Он:

- регистрирует и аутентифицирует пользователей;
- выдаёт JWT access и refresh;
- проверяет роли student/teacher и владение сущностями;
- создаёт сессии и исходные очереди;
- обеспечивает правила reorder, locked и frozen;
- меняет статусы waiting/called/done/skipped/absent;
- рассчитывает примерные интервалы;
- обновляет статистику фактического обслуживания;
- публикует realtime-события;
- принимает Telegram webhook для привязки аккаунта;
- отдаёт health-состояние PostgreSQL, Redis и флаг demo-mode.

Ключевая мысль для комиссии: backend — единственное место принятия бизнес-
решений. React предлагает действие, но разрешает или запрещает его FastAPI.


7. JWT Auth
===========

После успешного входа backend выдаёт два токена:

- access-токен короткоживущий; он прикладывается к API-запросам;
- refresh-токен долгоживущий; по нему можно получить новый access без пароля.

В токене есть user id, роль и тип токена. Backend не доверяет одной роли из
токена: он сверяет пользователя и права на конкретный объект в базе.

Для demo-токена добавляется признак demo. Он позволяет показывать демо-управление
только синтетическим аккаунтам. Telegram не используется как способ входа:
он лишь привязывается к уже существующему аккаунту.


8. Связь «FastAPI ↔ PostgreSQL»
==============================

FastAPI работает с PostgreSQL через SQLAlchemy. SQLAlchemy переводит операции с
Python-моделями в SQL. Alembic последовательно меняет схему базы при обновлениях.

PostgreSQL — источник истины. В нём хранятся:

- пользователи и группы;
- сессии преподавателей;
- записи очереди и их абсолютные позиции;
- locked, lock_reason и обязательная причина отказа absence_reason;
- время вызова и завершения;
- ServiceStat с EMA и variance;
- история перемещений QueueMoveLog;
- журнал и статус Telegram-уведомлений NotificationLog.

Почему не хранить очередь только в памяти или Redis
---------------------------------------------------
Процесс backend можно перезапустить, Redis можно пересоздать, соединение клиента
может оборваться. Состояние очереди всё равно должно сохраниться. Поэтому
долговременные данные находятся в PostgreSQL, а контейнер использует persistent
volume.


9. Redis Pub/Sub
================

Redis здесь — быстрая шина событий, а не основная база. После изменения очереди
backend публикует короткое событие в канал «session:<id>».

Подписчики:

- WebSocket backend получает событие и отправляет его открытым браузерам;
- Telegram worker получает событие и проверяет, кому нужно уведомление.

Pub/Sub не хранит историю сообщений. Если клиент был отключён, старое событие он
не получит. Это допустимо, потому что после reconnect или через polling клиент
запрашивает полное актуальное состояние из PostgreSQL.

Если Redis временно недоступен, сохранённую бизнес-операцию нельзя откатывать:
данные уже находятся в PostgreSQL. Пострадает только мгновенность обновления,
которую затем компенсирует повторное чтение API.


10. Связь «FastAPI → Redis → браузеры»
======================================

1) backend успешно сохраняет новое состояние в PostgreSQL;
2) публикует событие с типом, session_id, event_id и временем;
3) WebSocket-подписчик получает событие;
4) React понимает, что очередь изменилась, и перечитывает её;
5) оба окна — преподавателя и студента — показывают одно состояние.

Событие является сигналом «данные изменились», а не новым источником истины.
Это уменьшает риск расхождения между вкладками.


11. Telegram worker
===================

Это отдельный процесс, чтобы медленный или временно недоступный Telegram не
тормозил основной HTTP-запрос пользователя.

Worker:

- подписан на события «session:*» в Redis;
- находит нужных получателей и шаблон уведомления;
- проверяет NotificationLog, чтобы одно событие не отправить повторно;
- периодически формирует мягкие уведомления по приближению времени;
- повторяет доставку неудачных сообщений;
- вызывает Telegram Bot API через HTTPS.

В MVP есть три типа уведомлений:

- soft — очередь приблизилась, пора планировать подход;
- buffer — студент следующий, нужно быть рядом;
- hard_call — можно заходить.

Telegram — только дополнительный канал. Если он недоступен, сама очередь в
браузере продолжает работать.


12. Связь «Telegram ↔ система»
==============================

Исходящий путь:

Redis-событие → worker → проверка базы и дедупликация → HTTPS-запрос sendMessage
в Telegram Bot API → сообщение студенту.

Входящий путь для привязки:

Telegram → HTTPS webhook через NGINX → FastAPI → проверка секретного заголовка →
обработка одноразового кода → сохранение telegram_id в PostgreSQL.

Для локальной разработки вместо публичного webhook worker умеет long polling.
Webhook и long polling — два альтернативных способа получать входящие сообщения;
их не следует одновременно включать для одного бота.


13. Как считается примерное время
=================================

До начала сессии
----------------
Берётся локальная дата и время вуза в зоне Asia/Yekaterinburg. Для каждой позиции
добавляется duration_default. Например, старт 19:45 и 15 минут на студента дают
первое окно 19:45–20:00.

Во время сессии
---------------
До первого завершения оценкой служит duration_default. После каждого done
backend измеряет фактическое время «finished_at - called_at» и обновляет EMA:

EMA_new = 0,3 × real_time + 0,7 × EMA_previous.

Свежий результат влияет на прогноз, но единичный выброс не ломает его полностью.
Variance отражает разброс фактического времени и нужна для честной ширины
диапазона. До накопления статистики используется стартовая неопределённость,
поэтому окно не должно схлопываться в одну точку.

Capacity — число параллельных каналов. Каждый следующий waiting-студент
назначается каналу, который освободится раньше. При свободных параллельных каналах
у нескольких студентов начало интервала может совпадать — это правильная модель,
а не ошибка.

Важно: это прогноз, а не обещание точного времени. Поэтому интерфейс говорит
«Примерно», а система показывает диапазон.


14. Ключевые правила очереди
============================

- Студент двигает только собственную waiting-запись.
- Проверка выполняется на backend.
- Нельзя занять позицию, уже закреплённую locked-записью.
- Locked-запись сохраняет абсолютное место, остальные сдвигаются вокруг неё.
- Владелец locked-записи сначала должен снять фиксацию, затем двигаться.
- Frozen закрывает reorder всей очереди.
- Преподаватель может разморозить список, после чего reorder снова разрешён.
- Каждый успешный reorder пишется в QueueMoveLog: кто, когда, откуда, куда.
- lock_reason необязателен и относится к фиксации места.
- absence_reason обязателен и относится только к отказу от конкретной сессии.
- Отказ не удаляет историю и не затрагивает другие сессии студента.


15. Что происходит при сбоях
============================

Backend перезапустился
----------------------
Состояние остаётся в PostgreSQL. После старта применяются миграции, а клиент
перечитывает очередь.

Redis перезапустился
--------------------
Можно пропустить realtime-событие, но данные не теряются. Polling и повторный
API-запрос восстанавливают экран.

Telegram недоступен
-------------------
Основная очередь продолжает работать. Неудача фиксируется в NotificationLog,
worker может повторить доставку.

Frontend или WebSocket отключился
---------------------------------
После возвращения клиент запрашивает текущее состояние; ему не нужно проигрывать
все пропущенные события.

PostgreSQL недоступен
---------------------
Это критический сбой источника истины. /health вернёт 503, а изменяющие операции
не должны притворяться успешными.


16. Что было упрощено на схеме
==============================

Чтобы слайд читался за несколько секунд, на нём не показаны:

- Alembic, который управляет версиями схемы БД;
- JWT access/refresh как детали каждого API-запроса;
- NotificationLog и повторные попытки доставки;
- fallback polling раз в 5 секунд;
- Certbot/Let's Encrypt для выпуска сертификата;
- отдельные Docker volumes;
- CI GitHub Actions;
- demo seed и автоматический demo reset.

Это не отсутствующие части системы, а сознательно скрытые детали второго уровня.


17. Что в исходной схеме стоило исправить
=========================================

Надпись «Redis Pub/Sub + EMA-расчёт времени» между PostgreSQL и Telegram Bot API
смешивала три разные ответственности.

Правильнее говорить так:

- ETA/EMA считает FastAPI на основе данных PostgreSQL;
- Redis доставляет события об изменениях;
- Telegram worker получает события и вызывает Telegram Bot API;
- worker при необходимости читает PostgreSQL и пишет журнал доставки;
- Telegram Bot API не является частью нашей базы и не рассчитывает ETA.

Также JWT — не отдельный сервис рядом с FastAPI. Это механизм внутри backend:
FastAPI создаёт токен и проверяет его на защищённых запросах.


18. Готовый устный ответ комиссии
=================================

«Пользователь работает с React-приложением через единый адрес NGINX. Обычные
запросы и WebSocket NGINX направляет в FastAPI. Backend проверяет JWT, роль и
права на конкретную сессию, выполняет бизнес-операцию и сохраняет её в
PostgreSQL — это наш источник истины. После успешной записи backend публикует в
Redis событие. Его получают WebSocket-клиенты для живого обновления и отдельный
Telegram worker для уведомлений. Если realtime временно пропал, данные не
теряются: клиент перечитывает состояние из PostgreSQL через API. ETA тоже считает
backend: сначала из нормативной длительности, затем уточняет по EMA фактических
завершений и распределяет студентов по реальному числу параллельных каналов».


19. Совсем короткая версия на 20 секунд
=======================================

«NGINX — вход, React — интерфейс, FastAPI — правила, PostgreSQL — надёжная память,
Redis — мгновенные сигналы, отдельный worker — Telegram. Сначала сохраняем
операцию в PostgreSQL, затем сообщаем о ней через Redis. Поэтому быстрые живые
обновления не жертвуют сохранностью данных».
