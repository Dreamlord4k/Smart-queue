# Промпт для реализации проекта: «Умная очередь на сдачу лабораторных и экзаменов»

> Этот документ — полная техническая спецификация. Используй его как единственный источник правды при генерации кода. Если что-то не описано явно — выбирай простейшее решение, совместимое с описанной архитектурой, и явно комментируй это в коде.

## 0. Роль и задача

Ты — full-stack разработчик. Нужно реализовать рабочий MVP веб-сервиса «умной очереди» для сдачи лабораторных работ и экзаменов в вузе. Срок разработки — 2 дня, поэтому приоритет: работающий сквозной сценарий важнее количества фич. Весь код должен быть в одном репозитории, готовом к локальному запуску через `docker-compose up`.

## 1. Проблема и контекст

Студенты стоят в живой очереди на сдачу лабораторных/экзаменов часами (реальные случаи — до 3 часов), не зная точного времени своей сдачи. Действующая практика в вузе — учёт вручную через Google Forms/Sheets со статичным списком без пересчёта времени и без уведомлений. Задача — заменить это на систему, которая:
- показывает каждому студенту, к кому, куда и во сколько примерно его ждут;
- пересчитывает время в реальном времени по факту хода приёма (кто-то быстрее/медленнее);
- уведомляет студента заранее и в момент, когда пора подходить;
- даёт преподавателю простой интерфейс управления потоком.

Реализация должна быть **полностью программной** — никакого дополнительного оборудования, сенсоров или камер. Единственный источник данных о ходе очереди — действия пользователей в приложении (нажатия кнопок).

## 2. Пользователи и роли

- **Студент** (`role: student`) — состоит в одной или нескольких очередях одновременно (разные предметы/преподаватели), видит расчётное время, получает уведомления.
- **Преподаватель** (`role: teacher`) — создаёт и ведёт сессии приёма, управляет очередью.
- Отдельная роль администратора не нужна для MVP.

## 3. Функциональные требования

### 3.1 Преподаватель

1. Регистрация/логин (email или ФИО + пароль).
2. Создание сессии приёма:
   - предмет, аудитория, дата, время начала;
   - длительность приёма на одного студента (число минут, редактируемое и до, и во время сессии);
   - `capacity` — сколько студентов принимается одновременно (по умолчанию 1, редактируемо);
   - выбор участников: мультивыбор одной или нескольких групп целиком **и/или** добавление отдельных студентов вручную (поиск по имени) — то есть кастомная очередь из разных групп.
3. После сохранения сессии система в той же транзакции создаёт записи очереди для всех выбранных студентов: каждый сразу является участником, порядок по умолчанию — алфавитный. RSVP и отдельное подтверждение участия отсутствуют.
4. Экран управления сессией (один экран, без лишней навигации):
   - список участников по порядку с текущим статусом каждого и расчётным временем;
   - просмотр отдельно `lock_reason` (почему зафиксировано место) и `absence_reason` (почему студент отказался от этой сессии);
   - кнопка «Заморозить список» — после неё никто из студентов больше не может менять порядок;
   - кнопка «Завершить текущую» — завершает приём текущего студента(ов) в освободившемся канале, фиксирует реальное время, немедленно поднимает в этот канал следующего по очереди (без отдельного тапа «вызвать следующего»);
   - кнопка «Пропустить» (студент не пришёл — статус `skipped`, канал сразу освобождается для следующего);
   - кнопка «Добавить участника» (на лету, например опоздавший студент; новая активная запись добавляется в конец очереди);
   - кнопка «Закрыть сессию» (сессия окончена, показывается итоговый отчёт: сколько принято, средняя длительность, сколько было пропущено).

Перед переводом сессии в `active` преподаватель должен заморозить список (`frozen=true`); API не начинает приём для незамороженного порядка.

### 3.2 Студент

1. Регистрация/логин (ФИО + группа + пароль). Сессия должна сохраняться надолго (без повторного логина при каждом визите — access+refresh токены).
2. Главный экран — дашборд «Мои очереди»: карточка каждой активной или предстоящей сессии содержит предмет, преподавателя, аудиторию, дату и время, текущую позицию, ETA и статус участия. Карточки независимы и открывают конкретную очередь. Если у карточек одного дня пересекаются расчётные интервалы сессий, интерфейс может показать визуальное предупреждение; MVP не меняет позиции и не назначает приоритет автоматически.
3. Экран конкретной очереди — две колонки:
   - **Слева** — список всех участников очереди, по умолчанию отсортированный по алфавиту. Студент может drag-and-drop переставить **только свою собственную** карточку (не чужие), и только на место, которое ещё не зафиксировано другим студентом. Каждая карточка — чекбокс «зафиксировать место»; при отметке появляется необязательное текстовое поле «указать причину» (видна преподавателю), которое можно пропустить. Как только текущий студент отмечен преподавателем как принятый, его карточка анимированно исчезает из списка.
   - **Справа** — динамический таймер: расчётное время своей защиты (диапазон, не точная секунда), плюс подписи «сейчас принимают: …» и «далее в очереди: …».
4. Действие «Не смогу участвовать»: студент подтверждает отказ от **этой** сессии и может необязательно указать свободным текстом `absence_reason`. Запись сохраняется в истории, исключается из активной очереди, а позиции и ETA остальных пересчитываются. Отказ не изменяет другие очереди студента.
5. Привязка Telegram (кнопка «Получать уведомления в Telegram» → бот присылает код → студент вводит на сайте → бэкенд линкует `telegram_id` к аккаунту).
6. Получение уведомлений трёх типов (см. §6.2):
   - мягкое — «скоро ваша очередь, примерно через X–Y мин»;
   - жёсткое-буфер — «подходите к кабинету» (когда становится следующим на освобождающийся канал);
   - жёсткое-финал — «заходите» (когда вызван).

### 3.3 Участие и отказ от конкретной сессии

1. Выбор студентов при создании сессии — это добавление в очередь, а не приглашение на RSVP. Создание `Session` и всех исходных `QueueEntry` атомарно: уникальные студенты сортируются по `full_name` (при равенстве — по `id`) и получают последовательные позиции.
2. Пока запись имеет активный статус `waiting` или `called`, студент считается участником этой очереди. Нажатие «Не смогу участвовать» переводит только его `QueueEntry` в `absent`; причина необязательна. Если отказ происходит при `called`, канал освобождается и обрабатывается так же, как при пропуске: в него вызывается следующая активная запись.
3. `absent` не удаляется и остаётся доступной преподавателю вместе с `absence_reason`, но не участвует в активном списке, вычислении позиций, ETA или вызове следующего.
4. Пустая активная очередь никогда сама не переводит `Session` в `cancelled`. Статусом сессии, в том числе ручной отменой при необходимости, управляет преподаватель.

## 4. Ограничения по данным

- Все демо-данные — синтетические, генератор должен лежать в репозитории отдельным скриптом (см. §13).
- Реальные данные пользователей (если кто-то тестирует своими) — тоже допустимы, но обрабатываются так же.
- Запрещённые поля, которые НЕЛЬЗЯ добавлять никуда в модель данных: здоровье, доход, национальность, биометрия, точная геолокация.
- У каждого поля в модели данных, которое не самоочевидно, добавь в коде/README комментарий «зачем оно».
- `lock_reason` — это свободный текст, который пишет сам студент по желанию; не структурировать, не классифицировать, не требовать обязательного заполнения. Не добавлять отдельных структурированных полей для причин (например, отдельного поля «состояние здоровья») — это прямое нарушение запрета на такие данные.
- `absence_reason` — отдельный от `lock_reason` свободный необязательный текст об отказе от конкретной сессии. Его также нельзя структурировать или классифицировать; он виден преподавателю только этой сессии.
- Наружу (сторонним сервисам, кроме Telegram Bot API для уведомлений) ничего не должно уходить.
- Обязательна кнопка/эндпоинт «удалить мой профиль» (полное удаление аккаунта и связанных записей).

## 6. Бизнес-логика

### 6.1 Расчёт ETA

**До старта сессии** (status=planned):
```
planned_time[i] = start_time + i * duration_default
```
где `i` — позиция студента в очереди (0-индексация).

**После старта, при каждом переходе записи в статус `done`:**
```
real_time = finished_at - called_at   (секунды)
ema_estimate = alpha * real_time + (1 - alpha) * ema_estimate_prev
```
`alpha = 0.3` (константа, вынести в конфиг). Для первого наблюдения `ema_estimate = real_time`.

Обновлять `variance` как скользящую оценку дисперсии реальных времён (например, экспоненциальное скользящее значение квадрата отклонения от `ema_estimate`). Во всех формулах ниже активная очередь включает только записи `waiting` и `called`; `absent`, `done` и `skipped` в неё не входят.

**Live-пересчёт ETA при `capacity = 1`:**
```
remaining_ahead = position[j] - current_position
eta_seconds[j] = remaining_ahead * ema_estimate
eta_range[j] = [now + eta_seconds[j] - k*sqrt(variance), now + eta_seconds[j] + k*sqrt(variance)]
```

**Live-пересчёт ETA при `capacity = C > 1`** (несколько студентов принимаются параллельно):
```
channel_free_at[1..C] = now  (для занятых каналов — момент их ожидаемого освобождения:
                               called_at + ema_estimate; для свободных — now)

для каждого waiting-студента по порядку (по возрастанию position):
    ch = индекс канала с минимальным channel_free_at
    eta[студент] = channel_free_at[ch]
    channel_free_at[ch] += ema_estimate
```
Это жадное распределение по каналам (кто освободится раньше — тот и берёт следующего), пересчитывается целиком при каждом изменении.

`k = 1` по умолчанию. Показывать студенту диапазон, а не точную секунду.

Пересчёт запускать при каждом событии, меняющем состояние активной очереди (`done`, `skip`, `absence`, `reorder`, фиксация места, добавление участника), а не по таймеру — таймер используется только для фоновой рассылки мягких уведомлений (см. ниже). После отказа позиции активных записей нормализуются без пропусков.

### 6.2 Уведомления — три типа, разная логика триггера

1. **Мягкое (soft), по времени.** Фоновая задача каждые ~30–60 секунд пересчитывает `eta_seconds[j]` для всех waiting-записей текущей активной сессии. Если `eta_seconds[j]` впервые за сессию опустился ниже порога (константа, например 15 минут = 900 сек) — отправить уведомление «скоро ваша очередь, ETA X–Y мин» и залогировать в `NotificationLog` (чтобы не слать повторно).

2. **Жёсткое-буфер (buffer), по событию.** Сразу после того как запись переходит в `done` или `skip` и пересчитываются позиции — найти запись с новой `position = current_position + 1` (то есть второй в очереди) и отправить «подходите к кабинету, будьте рядом».

3. **Жёсткое-финал (hard_call), по событию.** Одновременно с (2) — найти запись с новой `position = current_position` (первый, кого нужно вызвать) и отправить «заходите, ваша очередь».

Все три канала используют один и тот же механизм доставки (см. §10), различается только текст и триггер.

### 6.3 Self-service реордер, фиксация, отказ и заморозка

- **Кто может двигать:** до заморозки студент может drag-and-drop передвинуть **только свою собственную** запись (со `status=waiting`, пока `locked=false`). Перетаскивание чужих карточек запрещено на уровне API, не только UI.
- **Куда можно встать:** целевая позиция должна быть **не занята зафиксированной записью** — то есть нельзя вставить себя на место, которое уже `locked=true` у другого студента. Технически это лучше реализовать не через «позицию-число», а как **вставку относительно списка**: студент выбирает «встать перед/после карточки X», бэкенд проверяет, что X (и вообще место вставки) не заблокировано, и только тогда пересчитывает `position` у всех задетых записей. Если `session.frozen=true` — реордер запрещён полностью, для всех.
- Каждое перемещение пишет строку в `QueueMoveLog` (`moved_by` тут всегда равен `student_id`, но поле оставляем для единообразия истории и будущей отладки).
- **Фиксация места:** студент ставит чек-марк на своей записи → `locked=true`, опционально указывает `lock_reason` (свободный текст, необязательный, виден только преподавателю этой сессии). После фиксации свою запись не может двигать даже сам студент, пока не снимет чек-марк.
- **Отказ от участия:** студент может только для своей записи вызвать «Не смогу участвовать», передав необязательный `absence_reason`. Запись получает `status=absent`, остаётся в БД для истории и не может быть физически удалена этим действием. Это не влияет ни на одну запись того же студента в других сессиях.
- **Заморозка:** преподаватель устанавливает `session.frozen=true` отдельным действием «Заморозить список». `locked` относится к одной карточке, а `frozen` запрещает любой реордер всей очереди. Начинать приём следует уже после заморозки порядка.
- «Пропустить»: пометить запись `skipped`, НЕ удалять из таблицы (нужно для статистики no-show), освободить канал (`channel=null`) для следующего по очереди. По умолчанию пропущенный не возвращается в очередь автоматически — препод/студент может вручную вернуть его в waiting и перетащить на нужную (незафиксированную) позицию.
- Добавление участника на лету: вставляется в конец текущей очереди (`position = max(position) + 1`).
- «Завершить текущую»: находит запись в статусе `called` с освобождающимся каналом → переводит в `done`, `finished_at=now`, обновляет EMA по формуле из §6.1 → немедленно берёт из `waiting` (по возрастанию `position`) следующую свободную запись → переводит её в `called`, `channel = освободившийся номер` → пересчёт ETA для всех оставшихся waiting (см. формулу с `capacity` в §6.1) → каскад уведомлений (см. §6.2) на новую текущую и новую «следующую на очереди» запись.

## 7. API

Все эндпоинты, кроме регистрации/логина, требуют JWT в заголовке `Authorization: Bearer <token>`. Роль проверяется на бэкенде (teacher-only эндпоинты недоступны студентам и наоборот).

```
POST   /auth/register          { full_name, password, role, group_id? }
POST   /auth/login             { full_name, password } -> { access_token, refresh_token }
POST   /auth/refresh           { refresh_token } -> { access_token }
DELETE /auth/me                -- удалить свой аккаунт и связанные данные

GET    /groups                 -- список групп (для формы регистрации/создания сессии)

POST   /sessions               (teacher) { course_name, room, date, start_time, duration_default, capacity, group_ids[], student_ids[] } -- сразу создаёт алфавитную очередь
GET    /sessions/mine          (teacher) -- сессии, которые я веду
PATCH  /sessions/{id}          (teacher) { status?, duration_default? } -- преподаватель стартует только frozen-сессию, ставит на паузу/закрывает или вручную отменяет, меняет длительность на лету
POST   /sessions/{id}/freeze   (teacher) -- установить frozen=true; повторный вызов идемпотентен
POST   /sessions/{id}/participants        (teacher) { student_id } -- добавить на лету
DELETE /sessions/{id}/participants/{eid}  (teacher)

GET    /sessions/{id}/queue    -- полное текущее состояние очереди + ETA по каждому (доступно и teacher, и участникам)
PATCH  /sessions/{id}/queue/reorder       (student) { entry_id, target_entry_id?, placement: before|after } -- только собственная waiting-запись до freeze
POST   /sessions/{id}/queue/{eid}/done    (teacher) -- завершить текущего, зафиксировать real_time, обновить EMA, каскад уведомлений
POST   /sessions/{id}/queue/{eid}/skip    (teacher)

GET    /students/me/queues     (student) -- все активные/предстоящие сессии с собственной записью, включая absent; карточка содержит ETA (если активен) и статус участия
POST   /students/me/queues/{eid}/absence  (student) { absence_reason? } -- пометить себя absent в одной сессии, без удаления записи

POST   /telegram/link/init     (student) -- сгенерировать одноразовый код для привязки
POST   /telegram/webhook       -- вебхук от Telegram Bot API (входящие сообщения, в т.ч. код привязки)

WS     /ws/sessions/{id}       -- живые обновления состояния очереди (или long-polling, если WS не успеваете)
```

## 8. Реалтайм-слой

- Использовать Redis как pub/sub брокер: при любом изменении состояния очереди (done/skip/absence/reorder/lock/freeze/add) публиковать событие в канал `session:{id}`.
- Backend держит открытые WebSocket-соединения клиентов, подписанных на нужную сессию, и пересылает им обновлённое состояние очереди (не весь объект — достаточно списка `{entry_id, position, status, eta_range}`).
- Если WebSocket не успеваете реализовать за отведённое время — временный fallback: long-polling каждые 5 секунд на `GET /sessions/{id}/queue`. Явно пометить в коде как временное решение.
- В Redis же можно держать текущее «горячее» состояние очереди (кэш) для быстрого чтения, источник истины — Postgres.

## 9. Аутентификация

- Обычная связка email/ФИО + пароль (bcrypt/argon2 для хэша).
- JWT access token (короткий TTL, например 15 минут) + refresh token (длинный TTL, например 30 дней), refresh хранить как httpOnly cookie либо в защищённом хранилище на клиенте.
- Роль (`student`/`teacher`) — поле в токене, используется для авторизации эндпоинтов.
- Telegram — НЕ метод входа, а канал уведомлений, привязываемый к уже существующему аккаунту:
  1. Студент в личном кабинете нажимает «Привязать Telegram».
  2. Бэкенд генерирует одноразовый короткий код, привязанный к `user_id`, с TTL (например 10 минут).
  3. Студент открывает бота, отправляет `/start <код>` (или просто присылает код текстом).
  4. Бот через вебхук передаёт код на бэкенд, бэкенд находит по коду `user_id` и записывает `telegram_id`.

## 10. Telegram-бот

- Один бот на весь сервис (не на сессию/группу).
- Deep link для быстрого захода: `t.me/<BotName>?start=<payload>` — можно использовать для привязки (payload = код привязки) или для прямого перехода к просмотру конкретной сессии.
- Отправка уведомлений — обычный `sendMessage` через Bot API по сохранённому `telegram_id`.
- Формат сообщений — короткий, без форматирования сложнее bold/emoji, три шаблона под три типа уведомлений из §6.2.
- Вебхук должен быть на HTTPS-домене (см. §12 — обязательно настроить Let's Encrypt).

## 11. Технологический стек (рекомендации, не догма)

- Backend: FastAPI (Python) или NestJS (Node/TypeScript) — выбрать то, что команда пишет быстрее.
- База данных: PostgreSQL.
- Кэш/pub-sub: Redis.
- Frontend: один SPA (React/Vue/Svelte — на выбор), который открывается и как обычный сайт, и как Telegram Mini App (просто добавить `<script src="https://telegram.org/js/telegram-web-app.js">` — использовать по минимуму, никакой отдельной сборки не нужно).
- Реалтайм: WebSocket (Socket.io или нативный) либо long-polling fallback.
- Бот: python-telegram-bot / aiogram (если backend на Python) или node-telegram-bot-api (если на Node).

## 12. Инфраструктура и деплой

- `Dockerfile` для backend, `Dockerfile` для frontend, отдельный контейнер для бота (или общий с backend, если это один процесс).
- `docker-compose.yml`, поднимающий: backend, frontend, postgres, redis, бот, nginx.
- Nginx как reverse proxy: маршрутизация `/api/*` → backend, `/` → frontend, TLS-терминация.
- HTTPS обязателен (Telegram webhook его требует) — Let's Encrypt/certbot.
- Минимальный CI: GitHub Actions — на пуш в main собрать образы и задеплоить (или хотя бы прогнать линт/тесты, если будут).
- `/health` эндпоинт на backend для проверки живости.
- `.env.example` с полным списком переменных окружения (DB_URL, REDIS_URL, JWT_SECRET, TELEGRAM_BOT_TOKEN, PUBLIC_BASE_URL и т.д.).

## 13. Синтетический генератор данных

Отдельный скрипт (`scripts/generate_demo_data.py` или аналог), который:
- создаёт несколько групп и студентов в них (случайные ФИО);
- создаёт одного-двух преподавателей;
- создаёт минимум две сессии в один день с общим студентом и реалистичным составом участников; все исходные очереди создаются автоматически;
- эмулирует отказ одного студента с необязательной причиной, перестановку и фиксацию места в одной очереди, а затем заморозку списка;
- эмулирует ход приёма: скриптом дёргает `done`/`skip` с рандомизированной задержкой вокруг заданной средней длительности (например, нормальное распределение), чтобы на демо можно было показать живой пересчёт ETA без ручного клика 20 раз.

Скрипт должен лежать в репозитории, не быть скрытой логикой — по правилам данных это обязательное требование.

## 14. Экраны (описание, не готовый дизайн)

**Студент — логин/регистрация** → простая форма.

**Студент — дашборд «Мои очереди»** — главный экран со списком активных и предстоящих очередей. На каждой карточке: предмет, преподаватель, аудитория, дата и время, текущая позиция, ETA и статус участия. Карточки нескольких экзаменов одного дня видны одновременно; потенциальное пересечение времени помечается предупреждением без автоматического изменения очередей. Открытие карточки ведёт на экран конкретной очереди.

**Студент — экран очереди** — две колонки:
- слева: список участников по алфавиту (по умолчанию), drag-and-drop для незафиксированных записей, чекбокс «зафиксировать место» + опциональное поле причины, анимированное исчезновение карточки при завершении студента;
- справа: динамический таймер (диапазон ETA), подписи «сейчас принимают: …» / «далее в очереди: …», кнопка «Не смогу участвовать» с необязательным полем причины. После подтверждения карточка студента исчезает из активного списка, но преподаватель видит запись и причину в истории.
Обновление обеих колонок без перезагрузки страницы (WS/long-polling).

**Студент — настройки** — кнопка привязки Telegram, кнопка «удалить мой профиль».

**Преподаватель — логин/регистрация** → простая форма.

**Преподаватель — список моих сессий** → создать новую / открыть существующую.

**Преподаватель — создание сессии** → форма (предмет/аудитория/дата/время/длительность) + мультивыбор групп + поиск и добавление отдельных студентов.

**Преподаватель — управление сессией (главный рабочий экран)** — один экран: активный список участников по порядку (имя, статус, ETA), отдельная история отказов с `absence_reason`, `lock_reason` у зафиксированных карточек, кнопки «Заморозить список», «Готово»/«Пропустить» на текущем, «Пауза», «Закрыть сессию», поле добавления участника на лету.

**Преподаватель — итоговый отчёт после закрытия** — количество принятых, средняя длительность, количество пропущенных, сравнение «плановое время сессии» vs «фактическое».

## 15. MVP-приоритет

**Обязательно сделать (без этого демо не работает):**
1. Регистрация/логин с ролями, JWT.
2. Группы + создание сессии с мультивыбором групп/студентов и автоматической алфавитной очередью.
3. Экран «Мои очереди» у студента и экран управления у препода: отказ с причиной, заморозка, Готово/Пропустить, живой список.
4. EMA-расчёт ETA и его живое отображение у студента.
5. Хотя бы один канал уведомлений (Telegram) на три триггера из §6.2.
6. Синтетический генератор данных для демо.

**Сделать, если останется время:**
- Drag-and-drop реордер у препода.
- Пауза сессии.
- Итоговый отчёт после закрытия.
- Web push как резервный канал уведомлений вместо/вместе с Telegram.

**Осознанно НЕ делать в этом MVP:**
- Систему приоритетов/типов заявок.
- Несколько параллельных каналов уведомлений одновременно.
- Аналитические дашборды для администрации вуза.
- Любую аппаратную/сенсорную часть (камеры, кнопки на входе и т.д.).
- Полноценный OAuth через Telegram как способ входа.

## 16. Демо-сценарий для защиты

1. Запустить синтетический генератор — преподаватель создаёт сессию с ~10 студентами, и все они сразу появляются в алфавитной активной очереди.
2. Один студент нажимает «Не смогу участвовать» и указывает причину; показать, что он исчезает из активной очереди, преподаватель видит причину в истории, а сессия не отменяется.
3. Открыть «Мои очереди» этого студента: он видит несколько экзаменов в один день, независимые позиции/ETA и при необходимости предупреждение о пересечении.
4. Открыть одну очередь, передвинуть свою карточку и зафиксировать место с `lock_reason`; показать, что две причины не смешиваются и зафиксированное место недоступно для перестановки.
5. Преподаватель нажимает «Заморозить список»; подтвердить, что студент больше не меняет порядок.
6. Начать приём при `capacity = 2`: видно двух «сейчас принимают».
7. Нажать «Завершить текущую» несколько раз подряд с разной скоростью — показать, как у остальных студентов ETA и очередь пересчитываются вживую с учётом двух каналов.
8. Показать пришедшее в Telegram уведомление «подходите» и «заходите».
9. Закрыть сессию, показать итоговый отчёт (замер «до»: плановое время по расписанию; замер «после»: фактическое время + средняя точность ETA) — это и есть требуемые рубрикой «два замера: до и после», и человек (демонстратор) своими словами объясняет на защите, что произошло.
