# PRODUCT.md

## Проблема

Студенты стоят в живой очереди на сдачу лабораторных/экзаменов часами (реальные случаи — до 3 часов, неоднократно), не зная точного времени своей сдачи. Действующая практика в ИРИТ-РТФ УрФУ для пересдач — учёт вручную через Google Forms/Sheets со статичным списком, без пересчёта времени и без уведомлений.

## Аудитория

- **Студент** — сидит у аудитории, ждёт защиты своей работы.
- **Преподаватель** — ведёт приём, хочет управляемый поток вместо толпы под дверью.

## MVP — что входит

1. Аккаунты с ролями (студент/преподаватель), студенты разделены по группам.
2. Преподаватель создаёт сессию приёма: предмет, аудитория, дата, время начала, длительность на человека, `capacity` (сколько студентов принимает одновременно — настраивается каждым преподавателем по-своему).
3. **Дашборд «Мои сессии»** — преподаватель за день часто ведёт несколько подряд идущих пар с разными группами (лабы/защиты), поэтому у него должен быть список всех своих сессий (сегодняшних и предстоящих) с их статусами, а не экран только одной сессии. Архитектурно это уже поддержано (каждая `Session` — независимая сущность), нужен только сам список-дашборд с переходом в конкретную сессию.
4. Сразу при создании сессии все выбранные преподавателем студенты получают записи в очереди, отсортированные по алфавиту. RSVP («буду» / «не буду») отсутствует.
5. Преподаватель может добавить студента в уже созданную и идущую сессию (добавление участника на лету), не только при первоначальном создании.
6. Студент может нажать «Не смогу участвовать» и должен оставить свободный текст причины. Его запись сохраняется в истории этой сессии, но исключается из активной очереди; ETA остальных пересчитывается. Отказ не влияет на записи студента в других сессиях.
7. Главный экран студента — **«Мои очереди»**: активные и предстоящие сессии с предметом, преподавателем, аудиторией, датой и временем, позицией, ETA и статусом участия. Несколько сессий в один день отображаются одновременно; возможное пересечение времени можно пометить предупреждением без автоматической смены порядка или приоритета.
8. До заморозки студент может двигать **только свою** карточку в конкретной очереди (не чужие) и не может встать на место, уже зафиксированное другим студентом. Преподаватель может заморозить список; после этого порядок не меняется никем.
9. Чек-марк «зафиксировать место» + необязательное текстовое поле `lock_reason` (видно преподавателю). Это отдельная причина и не связана с `absence_reason` при отказе от участия.
10. Динамический расчёт времени (ETA) — пересчитывается по факту хода приёма и изменения активной очереди, диапазон, а не точная цифра.
11. Уведомления трёх типов: мягкое («скоро ваша очередь»), буферное («подходите к кабинету»), финальное («заходите»); канал — Telegram (привязывается к уже существующему аккаунту, не заменяет его).
12. Одна кнопка «Завершить текущую» у преподавателя — убирает текущего (анимированно у студентов), сразу поднимает следующего в освободившийся канал приёма.
13. Синтетический генератор демо-данных лежит в репозитории.

## Границы — что НЕ входит в MVP

- Система приоритетов/типов заявок отдельной сущностью.
- Несколько каналов уведомлений одновременно (только Telegram + live-обновление страницы как фоллбэк).
- Аналитические дашборды для администрации вуза.
- Любая аппаратная/сенсорная часть (камеры, кнопки на входе) — реализация полностью программная.
- Полноценный OAuth через Telegram как способ входа (только линковка к уже созданному аккаунту).
- Автоматическое перераспределение студентов между пересекающимися сессиями или система приоритетов очередей.

## Критерии успеха (демо)

- Полный цикл работает локально: регистрация → создание сессии с автоматической очередью → отказ одного студента с причиной → фиксация и заморозка порядка → приём → уведомление → закрытие сессии с отчётом.
- Замер «до/после»: плановое время сессии по расписанию vs фактическое время + средняя точность ETA — по рубрике хакатона это обязательные «два замера».
- ETA пересчитывается видимо и правильно при `capacity > 1` (несколько параллельных каналов приёма).

## Ограничения по данным (рубрика хакатона)

- Все демо-данные синтетические, генератор в репозитории; свои настоящие данные тоже допустимы.
- Запрещены поля: здоровье, доход, национальность, биометрия, точная геолокация.
- `lock_reason` при фиксации места — необязательный свободный текст, а `absence_reason` при отказе от конкретной сессии — обязательный свободный текст; их не структурировать и не классифицировать.
- Обязательна кнопка «удалить мой профиль» (полное удаление аккаунта и связанных записей).
- Наружу, кроме Telegram Bot API, ничего не уходит.
